STANDARD OPERATING PROCEDURE (SOP)
Complete CRUD-Based Web Application Development
HTML • CSS • JavaScript • React • Django • Spring Boot • Database

1. Purpose
This Standard Operating Procedure (SOP) provides a structured process for students to design, develop, test, document, and demonstrate a complete CRUD-based web application. The application may be developed using HTML, CSS, JavaScript, React, Django, Spring Boot, or similar modern web technologies.
2. Objective
The objective is to enable students to develop a functional full-stack web application that implements Create, Read, Update, and Delete (CRUD) operations with a frontend, backend, REST API, database, validation, testing, and documentation.

7. Development Procedure
7.1 Requirement Analysis
Identify the problem and target users.
Define the main entity/entities to be managed.
List all fields required for each entity.
Define Create, Read, Update, and Delete requirements.
Identify validation, search, filtering, and authentication requirements.
7.2 Project Planning
Select the frontend and backend technologies.
Select the database.
Define the application architecture.
Create the project folder structure.
Create a Git repository and establish a suitable branching/commit strategy.
7.3 Database Design
Identify tables/entities and attributes.
Define primary keys and appropriate data types.
Define relationships where required.
Apply suitable constraints such as NOT NULL and UNIQUE.
Create the database and verify connectivity from the backend.
7.4 Frontend Development
Create a responsive layout using HTML and CSS.
Develop forms for adding and editing records.
Create a page/table/card layout for displaying records.
Add buttons or controls for Edit and Delete operations.
Implement client-side validation.
Implement search/filter functionality where required.
7.5 Backend Development
Create the Django/Spring Boot backend project.
Create models/entities representing the database structure.
Implement service/business logic.
Create REST API endpoints.
Implement server-side validation.
Implement exception/error handling.

7.7 Frontend–Backend Integration
Connect the React/JavaScript frontend to the backend API using fetch or Axios.
Send and receive JSON data.
Display API results dynamically.
Refresh the interface after successful CRUD operations.
Display meaningful success and error messages.
Configure CORS when frontend and backend run on different origins.

9. Validation Requirements
Mandatory fields must not accept empty values.
Email fields must follow a valid email format.
Numeric fields must accept only appropriate ranges.
Duplicate unique values should be handled correctly.
Server-side validation must be implemented even when client-side validation exists.
Validation errors should be clearly communicated to the user.
10. Testing Procedure
Test each API endpoint independently using Postman.
Test Create with valid, missing, duplicate, and invalid data.
Test Read with empty and populated databases.
Test Update with valid and invalid record IDs.
Test Delete with valid and invalid record IDs.
Verify database values after every operation.
Test frontend responsiveness on desktop and mobile screen sizes.
Test error handling when the backend or database is unavailable.
11. Security and Quality Guidelines
Never hard-code passwords, API keys, or database credentials in source code.
Use environment variables for secrets and configuration.
Validate and sanitize user input.
Use appropriate authentication and authorization for protected applications.
Use parameterized ORM/database operations.
Keep frontend, backend, and database responsibilities separated.
Use meaningful variable, function, class, and API names.
12. Version Control Procedure
Create a Git repository for the project.
Commit changes regularly with meaningful commit messages.
Maintain a README file containing setup and execution instructions.
Do not commit passwords, secret keys, virtual environments, or build artifacts.
Push the final project to the approved Git repository.

18. Suggested Project Architecture

19. Completion Criteria
The project will be considered complete when the student has implemented and demonstrated all four CRUD operations, established reliable frontend-backend-database communication, completed validation and testing, submitted the source code and documentation, and is able to explain the major components and workflow of the application.
